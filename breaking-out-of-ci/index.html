01 · runners, containers, vms
a runner runs each job in a container, then throws it away
a container shares the host kernel
a VM brings its own kernel, behind the hypervisor
01 · who builds the container
docker and kubernetes hand every container to a runtime
the default one, under both: runc
runc draws the walls: namespaces, cgroups, mounts, then starts your process
the wall is as strong as runc, and the kernel under it
02 · the privileged build
CI builds images with docker build
it needs the Docker daemon: mount the host's docker.sock
that socket is the node's Docker, as root
run on the node, read every other job's secrets
02 · and it needs no privilege
CVE-2024-21626 · "Leaky Vessels" · runc · Jan 2024 
# ordinary build. no --privileged.
FROM alpine
WORKDIR /proc/self/fd/7    # fd 7 → a dir on the HOST
RUN cat ../../../etc/shadow  # reading the node now
no privileged flag. one line, and the build's working directory is the host's filesystem. patched in runc 1.1.12.

03 · move the boundary
don't harden the container, stop sharing the kernel
privileged becomes root of a throwaway VM
but how do you get an ephemeral, automated VM per job?
Kata swaps out runc: every pod in its own VM
03 · the demo · kata

04 · what it costs
startup
+6 s
one VM boot per job, on average
memory
~690 MiB
extra per job, flat whatever the job's size (we budget 768 Mi)
cpu
~1.3×
on syscall-heavy work; real compute is basically native
build
~3×
a cold Go compile, the one cost we haven't configured away yet
reliability
0
infra failures on the kata tier so far
05 · which jobs go where
natron-ci · runc
natron-ci-privileged · kata
unprivileged
lint · test · scans · Helm · Renovate
→ just use natron-ci
privileged
denied (Kyverno + PodSecurity, at admission)
dind · buildah · docker build
untrusted / fork code → natron-ci-isolated (kata, unprivileged) · in design
06 · takeaways
  • a runner runs hostile code by design
  • shared kernel: one escape owns everyone
  • Kata moves the boundary into a VM
  • untrusted → Kata. trusted → runc.
